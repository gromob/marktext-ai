# macOS 한자 변환 수정 및 확인 기록

기준: `7cd32b04` / `v0.21.2-ai.2`, 브랜치 `work/hanja-local`.

환경: Apple Silicon, Node 22.23.3, pnpm 10.33.4.

현재 상태: v4 실제 IME 기록에서 일반 문단·목록·표의 선택 전/후 변환, undo/redo, 문장 중간의 앞뒤 글자·공백 보존을 확인했다. 저장 파일의 한자·문단·목록·표 구조도 유지됐으며 사용자가 닫기·재열기 후 보존을 확인했다. 최종 검사도 통과했으며 이번 수정 관련 파일만 단일 커밋으로 보존한다. 푸시는 하지 않는다. Computer Use로 입력기를 조작하지 않는다.

## 최종 코드 검증 및 보존 범위

임시 입력 로그 계측을 제거한 최종 소스에서 Muya 단위 95개(13개 파일), desktop 편집 명령 검사 3개(1개 파일), Chromium IME·undo/redo 32개(6개 파일)가 모두 통과했다. `pnpm run typecheck`, 변경된 Muya 런타임·새 테스트의 ESLint, `git diff --check`도 통과했다. `pnpm run lint`는 종료코드 0, 오류 0/경고 166으로 완료됐으며 관련 없는 경고 정리는 하지 않았다.

커밋 범위는 Muya `content.ts`·`muya.ts`, desktop `listenForMain.ts`, 관련 단위·E2E 테스트 네 파일, 이 검증 기록까지 총 여덟 파일이다. 의존성·lockfile·AI 연결 및 관련 없는 기능은 변경하지 않는다. 임시 진단 프로필·로그·사용자의 검증용 Markdown 파일은 커밋하지 않는다. 확인한 범위의 미해결 실패는 없으며, 마지막 창을 닫으면 앱이 종료되는 기존 동작은 이번 한자 수정 범위에서 변경하지 않았다. 실제 macOS IME는 사용자 조작과 진단 기록으로 확인했고, headless 검사를 실제 입력기 검사로 대체해 표현하지 않았다.

## 2026-10-23 최종 수동 검증

v4 기록에 undo 10회, redo 8회가 있다. 일반 문단의 변환 전 선택은 collapsed=true와 false가 각각 기록됐다. 문장 중간의 `수학`, `공부`, `시간` 변환 전후에는 다른 글자와 공백이 유지됐다. 글머리 목록에서도 선택 없이 `수학`, 직접 선택한 `공부`를 각각 변환하고 undo/redo한 기록이 있다. 표의 첫 셀은 collapsed=true인 끝 커서에서 `수학`을 변환했고, 둘째 셀은 undo 시작 선택의 anchor=9/focus=7, collapsed=false로 `공부`를 직접 선택해 변환했다. 두 셀 모두 원문 복원과 한자 재적용을 확인했다. 동일 키 입력에서 undo가 반복 호출되던 현상은 v4에서 관찰되지 않았다.

저장된 `/private/tmp/marktext-hanja-retest-v4.md`에는 `數學` 3회, `工夫` 3회, `時間` 1회가 남아 있다. 알려진 시험 입력·단어 치환과 Markdown 표 정렬 공백을 정규화하면 시험 전 파일과 모든 줄이 일치한다. 따라서 추가 줄바꿈·문단 분리·다른 항목이나 셀 손상은 저장 파일에서 발견되지 않았다. 사용자는 저장·닫기·재열기를 수행했고 변환이 보존돼 보인다고 확인했다. 이 재열기 화면은 Computer Use로 검사하지 않았으며, 사용자 관찰과 디스크 파일 확인을 결합한 결과다.

앞선 실제 입력 기록의 Escape 원문 복원, v4의 새 한글 입력 및 표 안 방향키·Enter 이동도 확인 근거에 포함한다. 입력기 이름이나 모든 키보드 상태 조합을 빠짐없이 시험했다고 확장하지 않는다. 회귀 검사와 실제로 확인한 조작을 구분해 기록한다.

추가 시험을 요구할 미확인 필수 항목이나 새 실패는 없다. 최종 정리에서 임시 `HANJA_TRACE` 계측을 Muya 소스에서 제거했고 관련 검사를 통과했다. 이번 수정 관련 파일만 하나의 커밋으로 저장한다. 임시 진단 실행 파일·검증용 사용자 문서·로그는 저장소 밖에 두며 커밋하지 않는다. 아래 항목은 이전 조사 당시의 기록이다.

## Cmd+Z 후속 실패와 보완

### 2026-10-23: v4 단일 undo 성공 확인

사용자는 v4가 제대로 작동하는 것 같다고 보고했다. `/private/tmp/marktext-ime-v4-trace.jsonl`에서 history-live-before/after가 각각 한 건이며, undo 한 번으로 `새 입력 위치 →數學`이 `새 입력 위치 →수학`으로 복원됐다. 블록 경로는 전후 모두 `[1, "text"]`로 같았다. 이후 native 선택 기록의 anchor/focus는 모두 11, collapsed=true로 단어 끝 커서이며 강조 선택이 없었다. 변환·undo 전후 DOM과 블록 텍스트도 일치했다. 앞의 `새 입력 위치 →` 문구가 유지됐다.

따라서 새로 입력한 단어의 일반 문단 변환·단일 undo·커서 복원 사례는 실제 IME 통과로 기록한다. 이 v4 기록에는 redo 호출이 없으며 목록·표·다른 문장·파일 재열기도 확인되지 않았으므로 전체 완료로 확장하지 않는다. 실행 중인 앱의 HMR을 피하려고 소스 변경 및 계측 제거는 하지 않았고, 검증 기록만 갱신했다. 최종 커밋·푸시는 하지 않았다.

### 2026-10-23: 한 번의 Cmd+Z에서 undo 여섯 번 확인

사용자는 새로 입력한 `수학`을 변환한 뒤 Cmd+Z 한 번으로 한글·한자가 모두 없어지고 커서가 줄 앞으로 이동한다고 보고했다. 이번에는 내부 계측 기록을 확보했다. `/private/tmp/marktext-ime-current-trace.jsonl`의 마지막 호출 묶음에서 `165910181.9ms`부터 `165910207.7ms`까지 undo가 여섯 번 호출됐다. 첫 번째 undo는 `새 입력 위치 →數學`을 `새 입력 위치 →수학`으로 정상 복원했고, 두 번째는 `학`, 세 번째는 `수`를 지웠으며, 나머지는 그 이전 입력까지 되돌렸다. 이 실패의 직접 원인은 한자 역변환 operation이 아니라 단일 명령의 반복 전달임을 확인했다.

기존 앱에 이미 쌓인 수신기는 등록 방지 코드를 추가하는 것만으로 제거되지 않는다. 마지막 기록의 renderer 성능 시계도 장시간 실행 중인 창임을 보여 준다. 재마운트 여섯 번 후에도 IPC/bus의 undo·redo 명령이 각각 한 번만 전달되는 회귀 검사로 보강했으며 desktop 3개 검사가 통과했다. ESLint 및 diff 공백 검사도 통과했다.

기존 창을 닫거나 덮어쓰지 않고, 별도 프로필 `/private/tmp/marktext-ime-v4-profile`에서 `MarkText IME 진단 v4 — 새 실행`을 시작했다. 최초 시도에는 개발 서버가 종료돼 연결 거부가 발생했으므로 해당 새 프로세스만 종료하고 개발 서버를 재시작한 다음 다시 실행했다. 검증 파일 사본은 `/private/tmp/marktext-hanja-retest-v4.md`, 새 진단 기록은 `/private/tmp/marktext-ime-v4-trace.jsonl`이다. 네이티브 파일 열기 경로로 사본을 열었으며 키·마우스·IME 조작은 하지 않았다. 새 실행에서의 실제 IME 확인은 사용자 결과를 기다린다. 이후 검사 중 소스 변경으로 HMR을 유발하지 않는다. 계측 제거와 최종 커밋은 전체 사용자 검사 통과 후 진행한다.

### 최신 실패: undo 후 `수`만 남음

사용자는 커서 선택 복원 수정 후 Cmd+Z에서 `수학` 중 `수`만 남는다고 보고했다. 이후 사용자는 문서에 이미 있던 단어가 아니라 `수학`을 새로 입력하고 변환한 다음 Cmd+Z를 한 번 누른 경우라고 명확히 했다. 최신 실제 IME 결과는 실패 상태이며 해결 완료로 간주하지 않는다. 기존 native 기록에서도 변환 직전 `수학`, 확정 후 `數學`, 다음 키 입력 시 `수`인 DOM을 확인했다. 새로고침 이후에는 이전 Muya 인스턴스에 설치했던 history 래퍼가 적용되지 않아 이때 undo 호출 횟수·operation은 수집되지 않았다.

추가 검사에서는 마지막 음절 `학` 입력 직후의 이력을 지우지 않고 변환하면 첫 undo는 `수학`, 두 번째 undo는 `수`, redo 두 번은 `數學`으로 복원된다. 기존 문단·목록·표의 마지막 음절 검사에서도 변환 전 `clearHistory()`를 제거했다. 현재 소스로는 단일 undo의 음절 소실을 재현하지 못했다.

별도로 개발 HMR에서 앱 컴포넌트가 재마운트되면 `app.vue::onMounted`가 `LISTEN_FOR_EDIT`를 다시 호출하고, 같은 store에 IPC 및 bus 수신기를 중복 등록하는 결함을 확인했다. 회귀 테스트는 수정 전 두 개의 IPC 수신기를 확인하며 실패했다. `listenForMain.ts`에서 편집 명령 수신기를 한 번만 등록하도록 수정했고, 재등록 시도 후 단일 IPC/bus 명령이 undo 한 번만 발생시키는 검사가 통과했다. 실제 실패 원인인지 확인하려면 새로고침한 진단 창에서 사용자 검증이 필요하다. 다른 수신기나 기능은 변경하지 않는다.

진단 기간에만 `Muya._changeHistory`에 `__hanjaTraceInstalled` 창을 대상으로 직전·직후 operation·블록 경로·텍스트를 기록하는 임시 계측을 추가했다. 사용자 조작을 자동화하지 않으며, 원인 확인 후 커밋 전에 제거한다. 최신 실제 IME 결과를 기다리며 커밋과 푸시는 하지 않는다.

추가 자동 검증: desktop 수신기 테스트 3개, Chromium 관련 검사 32개 통과. 타입 검사·변경 파일 ESLint·diff 공백 검사 통과. 기존 Muya 단위 95개 통과 결과는 이전 단계 기록이며, 이번 추가 변경은 위 desktop/Chromium 검사로 확인했다. OpenCode의 지정된 로컬 모델에는 관련 함수 발췌만 읽기 전용으로 전달했다. 모델은 keyup 경합과 테스트의 이력 초기화를 가설로 제시했지만, 원인으로 확정하지 않았고 코드와 추가 검사로 검토했다.

최신 확인: 사용자는 Cmd+Z 후 원래 한글이 같은 위치에서 강조 선택되고, redo는 단어 끝 커서로 복원된다고 보고했다. 변환을 위해 코드가 임시로 만든 선택을 undo 시작 상태에 기록한 것이 원인이다. 자동 선택 전에 원래 커서 상태를 저장하도록 수정했다. 선택 없이 변환하면 undo 후 단어 끝 커서가 복원되고, 직접 선택한 경우에는 원래 선택을 복원한다.

중간 문단 회귀 검사에서 수정 전에는 선택 없는 경우만 실패하고 직접 선택한 경우는 통과했다. 수정 후 두 경우와 이전 번호 목록 커서 이력 검사가 모두 통과했다. 실제 macOS IME에서의 최신 수정은 사용자 재확인을 기다린다.

추가 사용자 결과: 맨 앞의 `수학`을 변환한 뒤 Cmd+Z를 누르면 아래 `1. 수학`으로 커서가 이동하고, Cmd+Shift+Z에서는 제자리로 돌아온다고 보고했다. 이후 사용자는 같은 위치에서 한글이 선택된 상태로 복원된다고 정정했다.

아래 번호 목록에서 먼저 편집해 이전 커서 이력을 남긴 다음, 맨 앞 일반 문단의 단어를 변환·undo하는 회귀 검사를 추가했다. 당시 소스에서는 같은 문단 경로와 `수학` 선택이 복원돼 통과했다. 한편 당시 개발 서버는 종료돼 있었고, 이전 진단 창에 최신 코드가 적용됐는지는 확인할 수 없었다. 구버전 실행이 원인이라고 확정하지 않는다.

기존 진단 프로필의 복구 파일을 별도 복사하고 개발 서버를 재시작했다. `MarkText IME 진단 v3 — 커서 복원 확인` 창에서 실제 Muya 인스턴스에 `_changeHistory`와 `_beginHanjaReconversion`이 로드됐음을 확인했다. 이 창은 undo/redo 직전·직후의 실제 선택 경로와 스택의 선택 경로를 읽기 전용으로 `/private/tmp/marktext-ime-current-trace.jsonl`에 기록한다. 후속 사용자 확인과 경로 기록에서는 같은 문단으로 복원됐고, 자동 선택 범위가 남는 차이를 확인했다.

사용자는 한글/영문 입력 상태에서 실행 취소가 다르게 보이고, 일부 글자나 줄이 함께 없어지며 커서가 엉뚱한 곳으로 이동하거나 Enter·오른쪽 화살표가 동작하지 않는 경우를 보고했다. 표의 수동 검증은 아직 하지 않았다.

자동 재현으로 두 문제를 확인했다.

- 빠른 한글 입력·문단 생성·한자 변환이 시간 기준의 하나의 undo 기록으로 합쳐졌다. 변환 직전 기록을 초기화했던 초기 테스트는 이를 놓쳤다. 초기화 없이 연속 동작하는 회귀 테스트를 추가했다.
- 조합 중 `Muya.undo()`를 호출하면 기존 문서와 DOM은 바뀌지만 블록의 조합 상태가 남았다. 조합 문자열은 redo에도 보존되지 않았고 이후 키가 정상 처리되지 않았다.

보완:

- `Content`는 한자 변환 전후에 지연된 문서 작업을 반영하고 undo 경계를 분리한다. 시작 경계에는 현재 선택도 기록해 다른 문단의 이전 커서가 복원되지 않도록 한다.
- `Muya.undo/redo`는 진행 중인 조합이 있으면 현재 네이티브 입력 요소를 blur해 브라우저가 조합을 확정하도록 한 다음 지연 작업을 반영하고 history를 변경한다. 브라우저가 아직 조합 중이라면 그 DOM을 history로 덮어쓰지 않는다. 조합 중이던 경우에는 변경 후 편집기에 포커스를 복원한다.
- 중간 문단의 `앞 수학 뒤`를 변환·undo했을 때 같은 문단 경로에서 원래 커서 또는 직접 지정한 선택이 복원되는 것을 검사했다. redo도 같은 문단에 적용된다.

## 중복 기록과 추가 수정

검증된 진단 창의 실제 입력에서는 다음 순서가 기록됐다.

1. `수학` 끝의 Option+Enter는 키 코드 229, `isComposing=true`, 선택 `[2,2]`였다.
2. 마지막 음절 `학`이 기존 범위 `[1,2]`에서 확정되고 `compositionend`가 발생했다.
3. 새 한자 조합이 시작됐지만 첫 후보 `修學`의 `beforeinput` 범위는 `[2,2]`였다. 원문을 대체할 범위가 없었다.
4. 바로 다음 `input`에서 DOM은 이미 `수학修學`이었다. 편집기 상태 반영 이후에 원문이 다시 붙은 것이 아니다.
5. 후보 `受學`, `數學`과 최종 확정은 모두 뒤쪽 `[2,4]`만 대체해 최종 결과가 `수학數學`이었다.

같은 순서를 CDP에서 재생하되 대체 범위를 명시하지 않으면 중복이 재현된다. 키를 누르는 즉시 원문을 선택하는 안은 마지막 음절 확정으로 선택이 사라졌고, 새 `compositionstart`에서 선택하는 안은 Chromium 조합이 취소돼 제외했다. 기존 음절의 `compositionend` 처리 직후 선택하는 안에서는 첫 후보 범위가 `[0,2]`가 되어 제자리 대체됐다.

추가 수정도 `content.ts` 한 파일에 한정한다. macOS Option+Enter에서 기존 선택은 보존하고, 선택이 없을 때 커서 바로 앞의 연속 한글 음절만 선택한다. 진행 중인 조합이 있으면 마지막 음절 확정 직후로 선택을 미룬다. 요청이 남아 있으면 keyup/blur로 해제해 이후 일반 입력에 적용되지 않게 한다. 문서 텍스트를 추측으로 잘라내거나 조합 중 DOM을 다시 만드는 보정은 하지 않는다.

현재 테스트는 외부에서 `replacementStart`/`replacementEnd`를 제공하지 않는다. 완료된 한글과 마지막 음절 조합 중인 한글을 각각 문단·목록·표에서 변환하고 후보 변경·실행 취소·다시 실행을 검사한다. 실제 입력기에서의 대체 범위와 취소 동작은 사용자 재확인 전까지 확정하지 않는다.

줄이 이동한 경우 다음을 구분한다.

- 창 너비를 늘리면 붙고 저장한 본문에도 내부 줄바꿈이 없으면 화면상의 자동 줄바꿈이다.
- 소스 모드/저장 파일에서 단어 앞에 `\n`이 있으면 실제 줄바꿈이다. 빈 줄로 분리되어 있으면 별도 문단 가능성이 있다. 표는 `<br>`도 확인한다.
- 한 단어만 있는 일반 문단의 저장 결과는 `數學` 또는 끝에 개행 하나가 붙은 `數學\n`이어야 한다. `수학數學`, 단어 앞 개행, 추가 빈 문단은 실패다.

실패 시 입력기·단축키, 선택 유무, 실제 표시, 저장된 Markdown을 함께 기록한다. 문서 내용은 시험용 단어만 사용한다. 이 확인 전에는 실제 IME 문제가 해결됐다고 확정하지 않는다.
